面试里被问「你写过代码规范吗」，大多数人的回答停在「命名用小驼峰、缩进 4 空格」。但如果面试官接着问「内存泄漏怎么系统性防」「RAII 到底解决了什么」「Qt 里 new 出来的对象谁来删」，很多人就卡壳了。

我是一名嵌入式工程师，日常在 STM32、FreeRTOS、嵌入式 Linux 上写 C/C++/Qt。对我而言这套规范不是面试八股，而是每天都在用的生存手册——在几十 KB RAM 的板子上，一次野指针不是崩掉一个进程，而是让整台设备变砖。所以这篇文章想同时做两件事：给面试准备者一条能自圆其说的主线，也给同行一个「从嵌入式约束反推规范」的视角。

文章不逐条抄规范，而是把华为三份 Linux 编码规范（C / C++ / Qt C++）串成一条演进线，看一套规范体系怎么随语言能力「长」出来。三份文档一句话定位：

- **C 规范**：管内存与边界，教你守住底线的防御式编程；
- **C++ 规范**：管资源与类设计，用 RAII 把「人肉守规矩」升级成「编译器帮你守」；
- **Qt 规范**：管 UI 与对象生命周期，用对象树解决 C++ 内存模型在 GUI 场景下的水土不服。

三份文档底层是同一个内核——**防御式编程**。但在嵌入式场景里，它上面还叠加着一层更硬的约束：代码体积、实时性、确定性、资源受限。读完这篇，你既能用一条线把「编码规范 / 内存 / 安全」类面试题串起来，也能理解规范里那些「看起来迂腐」的条款到底在防什么。

## 第一层 C 规范：守住内存与边界

C 语言的规范本质上是「内存和边界的安全手册」，也是面试最容易被深挖的一层。

### 内存管理闭环

野指针和内存泄漏是 C 面试的必考题。华为 C 规范把内存管理拆成一个完整闭环：

```c
// ❌ 常见错误：不判空、不置空
char *p = malloc(1024);
strcpy(p, src);          // p 可能为 NULL，直接崩

free(p);                 // 若 p 已释放，这里就是重复 free
```

```c
// ✅ 规范写法：判空 → 使用 → 置空，形成闭环
char *p = malloc(1024);
if (p == NULL) {
    return -ENOMEM;      // 1. 判空
}
/* 使用 p ... */
free(p);                 // 2. 成对释放
p = NULL;                // 3. 置空，防止野指针
```

面试会这么问：**「free 之后为什么要置 NULL？」** 答案不是玄学——`free` 后指针值不变，仍指向已释放内存，再次解引用就是未定义行为；置空后再次 `free(NULL)` 是安全操作，还能配合判空提前拦截误用。

这里有个嵌入式特有的视角：**在裸机 / RTOS 上，动态分配本身就是一种奢侈**。`malloc` 的返回时间不固定，堆碎片会越用越碎，所以很多嵌入式项目干脆用静态数组或内存池。华为规范里的「判空 → 成对 → 置空」三步，本质是把动态内存的不可控性压到一条底线：要么你别用，要么你守规矩。一个 128KB RAM 的板子，经不起几次泄漏。

### 缓冲区安全

```c
// ❌ 不安全：无长度上限，越界写入
strcpy(dst, src);
sprintf(buf, "%s", userInput);

// ✅ 安全版本
strncpy(dst, src, sizeof(dst) - 1);
snprintf(buf, sizeof(buf), "%s", userInput);
```

考点：**为什么 `strncpy` 仍要手动补 `\0`**——`strncpy` 在源串不短于 n 时不会补终止符，所以必须自己保证字符串以 `\0` 结束。

嵌入式里缓冲区溢出比桌面端更致命：栈往往只有几 KB，越界写会直接踩坏返回地址，而且这种崩溃常常在远离出错点的地方才爆发，极难定位。这也是为什么规范宁可啰嗦，也要强制边界检查。

### 类型与参数校验

- 用 `<stdint.h>` 的 `uint32_t`/`int32_t` 取代 `int`/`long`，消除跨平台长度不一致；
- 函数入口先做合法性校验：

```c
if (buf == NULL || len == 0) {
    return -EINVAL;
}
```

这背后是防御式编程的第一原则：**永远不信任入参**。对外接口尤其要守住这道闸门。

对嵌入式工程师来说，`stdint.h` 不只是「规范要求」，而是硬件寄存器位宽、外设协议字段对齐的基本功——一个 `int` 在 8 位单片机和 64 位 SoC 上宽度不同，写死 `int` 的代码换个平台就是隐患。

C 规范还特别区分了用户态与内核态：内核代码禁用 `malloc`/`printf`，改用 `kmalloc`/`kfree` 和 `pr_info`，且禁止浮点运算——这属于「Linux C 开发」特有的附加约束，面试中一笔带过即可。

**第一层小结**：C 规范教会我们守住内存和边界，但它依赖「人肉守规矩」——每处 `malloc` 都要记得判空、成对、置空。人总会漏，尤其当代码量一上来。这就是第二层要解决的问题。

## 第二层 C++ 规范：RAII 与类设计

到 C++，规范的重心从「人肉守规矩」转移到「用语言机制守规矩」。核心答案只有一个：**RAII（Resource Acquisition Is Initialization）**。

### 智能指针三件套

裸指针管理生命周期是 C++ 面试的送命题。华为规范给了清晰的分工：

```cpp
// 1. 独占所有权：unique_ptr 首选
std::unique_ptr<uint8_t[]> buf = std::make_unique<uint8_t[]>(1024);

// 2. 共享所有权：shared_ptr 少用，警惕循环引用
std::shared_ptr<TcpSession> session = std::make_shared<TcpSession>();

// 3. 观察者弱引用：weak_ptr 配合 shared_ptr 打破循环引用
```

面试会追问：**「shared_ptr 循环引用为什么泄漏？weak_ptr 怎么破环？」**——两个对象互相持有对方的 `shared_ptr`，引用计数永远不为零；用 `weak_ptr` 只「观察」不「持有」，引用计数不增加，环就断了。

### 类设计红线

这一节是「C++ 类规范」的高频考点集合：

```cpp
// ✅ 推荐：成员用初始化列表，不做失败操作
TcpSession::TcpSession() : fd_(-1), recvTotal_(0) {}

// ❌ 构造函数里 malloc / 打开文件 / 创建线程
//    失败无法向调用者返回，改用单独的 init()
```

- **构造函数禁止执行失败操作**：构造失败没有优雅的返回通道，只能靠抛异常，而异常在驱动/实时模块是被禁用的；
- **虚基类析构必须 `virtual`**，否则通过基类指针删除派生类对象时不会调用派生类析构，导致泄漏；
- **析构禁止抛异常**，建议加 `noexcept`；
- **不需要拷贝就用 `= delete` 禁用**，防止浅拷贝造成二次释放。

### 异常分级策略

华为的异常管理是「分场景」的，这也是面试里的冷门加分点：

- **驱动、协议栈、实时模块：全局禁用异常**（`-fno-exceptions`）；
- **上层业务服务：可控启用**，但析构函数、构造函数、`noexcept` 函数内绝不抛异常。

为什么嵌入式尤其禁异常？这不是「规范规定」四个字能打发的，背后是三个实打实的代价：

1. **代码体积**：异常的表驱动栈展开需要运行时支持，`-fno-exceptions` 能省下可观的 Flash/RAM，在资源受限的板子上这是刚需；
2. **实时性**：异常路径不可预测，抛出和展开的时间不确定，会破坏硬实时任务的确定性；
3. **上下文安全**：在中断处理函数、驱动回调里抛异常，栈展开无处可去，直接就是未定义行为。

所以嵌入式里「错误码 + goto 清理」这套看起来很土的写法，反而比异常更受欢迎——不是不会用，而是用不起。

### STL 安全

- `vector` 频繁扩容有性能隐患，提前 `reserve`；
- 无序查找优先 `unordered_map`/`unordered_set` 而非 `map`/`set`；
- 警惕迭代器失效：`erase` 和扩容后旧迭代器会失效。

**第二层小结**：C++ 用 RAII 把「记得释放」交给析构函数，把「记得检查」交给编译期，把守规矩从「自觉」变成了「机制」。但 RAII 管的是单个资源，管不了对象之间的层级关系——在 GUI 里，一个窗口下面挂几百个子控件，谁来统一回收、谁先谁后？这就是第三层要解决的。

## 第三层 Qt 规范：对象树与信号槽

Qt 是 C++ 在 GUI 场景的延伸，它引入两个独有的内存/通信模型，也是 Qt 面试的核心。

### 对象树：谁负责删

Qt 最大的心智模型是**对象树**：`new` 出来的 `QObject` 只要传入 `parent`，就挂到父对象下，父对象析构时自动回收所有子对象。

但这里有个著名的坑——**双重管理**：

```cpp
// ❌ 对象树 + 智能指针双重管理 → 双重释放崩溃
std::shared_ptr<QWidget> w(new QWidget(parent));

// ✅ 界面层级靠对象树，业务数据模型才用智能指针
//    一个 QObject 永远只由一种机制管理
```

面试会问：**「Qt 的对象树和 C++ 智能指针能一起用吗？」** 正确答案是「分场景，同一对象不能两种机制并存」，否则会被析构两次。

在广告机、HMI、车载屏这类嵌入式 GUI 里，界面是长生命周期、树状层级明确的对象，对象树恰好匹配这个模型——窗口、控件、弹窗天然构成父子关系，父对象一析构，整棵子树自动回收。反过来，如果用智能指针硬套界面层级，反而会掉进双重管理的坑。这也是为什么 Qt 在嵌入式 UI 领域能站住脚：它的内存模型和界面的真实结构是吻合的。

### 新旧 connect：编译期 vs 运行时

```cpp
// ❌ 旧式字符串：运行时才做字符串匹配，写错不报错
connect(timer, SIGNAL(timeout()), this, SLOT(slotTimerTimeout()));

// ✅ 新式函数指针：编译期类型检查
connect(timer_check_, &QTimer::timeout, this, &MainWindow::slotTimerTimeout);
```

考点：**「为什么弃用 SIGNAL/SLOT 宏？」**——宏展开后是字符串，参数不匹配只能运行时崩；函数指针写法在编译期就能拦住类型错误。

### 线程红线

Qt 规范有一条不可逾越的红线：**UI 控件只能在主线程操作**。

- 子线程不直接改控件，通过信号槽 `Qt::QueuedConnection` 异步通知主线程；
- 业务 worker 类 `moveToThread` 移入子线程，而不是继承 `QThread` 重写 `run`；
- 需要销毁对象用 `deleteLater()`，让它回到事件循环空闲时安全析构，避免「在槽函数里删发送者」这类崩溃。

### 字符串与国际化

所有用户可见字符串必须包 `tr()`，源码统一 UTF-8；禁止拼接后再翻译，要用占位符模式 `tr("总数：%1").arg(count)`——这样不同语言的语序才能正确适配。

**第三层小结**：Qt 用对象树解决 GUI 场景的层级回收，用信号槽解决跨线程、跨对象的通信。到这里，三份规范拼成了一个完整的能力图谱：C 守住底线，C++ 用机制守住资源，Qt 用模型守住 UI 的生命周期。

## 贯穿三层的共通思想

剥开三份规范的表层差异，底层是四个一致的原则：

1. **防御式编程**：判空、边界校验、返回值校验——「永远不信任输入」，C 的入口校验、C++ 的 `nullptr` 判断、Qt 的 `qobject_cast` 判空，都是同一件事。
2. **可读性优先**：命名见名知意、4 空格缩进、Doxygen 注释——注释解释「为什么做」，而不是复读「代码做了什么」。
3. **资源生命周期闭环**：C 的 `malloc/free` 成对、C++ 的 RAII、Qt 的对象树，本质都是「谁申请谁负责、谁创建谁回收」，只是自动化程度逐层升高。
4. **工具化门禁**：三份规范都强制 `-Werror`（警告当错误）、配合 cppcheck / clang-tidy / checkpatch.pl 做静态检查——靠工具把规范变成「编译不过」的硬约束，而不是靠自觉。

对嵌入式工程师来说，第四条尤其关键：板子上的 bug 不像桌面程序那样能开个调试器慢慢看，很多问题是「设备已经出货了才爆发」。所以能在编译期、静态检查期拦下的问题，绝不留到运行时。

这一条演进线，正是面试官想听到的「系统思维」：**规范不是死规则，而是语言能力与工程约束的映射。** 语言在进化（C → C++ → Qt），约束在叠加（内存安全 → 资源安全 → 生命周期安全），规范跟着一起长出来。

## 面试速记清单

> 面试前快速过一遍，每条都能展开成一段回答：

1. **野指针怎么防？** free/delete 后置 NULL，使用前判空，配合 RAII 少用裸指针。
2. **内存泄漏怎么系统性防？** 成对释放 → 智能指针 → RAII 封装资源 → Qt 对象树自动回收。
3. **RAII 是什么？** 把资源绑定到对象生命周期，构造获取、析构释放，异常安全。
4. **unique_ptr vs shared_ptr？** 独占 vs 共享；shared_ptr 警惕循环引用，用 weak_ptr 破环。
5. **为什么虚基类析构要 virtual？** 保证通过基类指针删除派生类时能正确调用派生类析构。
6. **构造函数能执行失败操作吗？** 不能，失败无法返回，改用 init() 接口。
7. **C++ 异常什么时候禁用？** 驱动/协议栈/实时模块禁用，上层业务可控启用。
8. **strcpy/sprintf 为什么禁用？** 无长度上限，越界写入，改用 strncpy/snprintf 并保证 `\0`。
9. **Qt 对象树能配智能指针吗？** 同一对象不能两种机制并存，否则双重释放崩溃。
10. **为什么弃用 SIGNAL/SLOT？** 运行时字符串匹配易错，改函数指针 connect 编译期检查。
11. **Qt 子线程能改 UI 吗？** 不能，必须通过信号槽异步回主线程。

掌握这 11 条，编码规范、内存管理、C++ 安全、Qt 架构这几类面试题，你都有了一条可以自圆其说的主线。

如果面试官再追问一句「这套规范和嵌入式有什么关系」，你可以把这条演进线反着说一遍：规范里的每一条「限制」，几乎都能追溯到嵌入式对体积、实时性、确定性的约束。能在几十 KB RAM 上活下来的代码，注定是一条一条约束堆出来的。
